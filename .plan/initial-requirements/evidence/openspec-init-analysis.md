## Executive summary

OpenSpec has two distinct initialization layers:

1. **Project initialization (`openspec init`)** creates the repository-local OpenSpec home and AI tool integrations:
   - `openspec/`
   - `openspec/specs/`
   - `openspec/changes/`
   - `openspec/changes/archive/`
   - optionally `openspec/config.yaml`
   - selected agent skills and/or slash command files.
2. **Change/artifact initialization** happens later through `openspec new change`, generated `/opsx:*` workflows, `openspec status`, and `openspec instructions`. It creates a change directory with `.openspec.yaml`; agents then write `proposal.md`, `design.md`, `tasks.md`, and delta spec files according to schema-driven instructions.

OpenSpec does **not** eagerly create every durable `openspec/specs/<domain>/spec.md` at project init. Durable spec docs are created or updated later by applying change-local delta specs, normally during sync/archive. For a brand-new spec domain, the archive/apply code creates a skeleton durable spec containing `# <Capability> Specification`, `## Purpose`, and `## Requirements`.

## `openspec init` entrypoints and options

## Directory and config creation

`InitCommand.execute()` coordinates the init flow:

- resolves the target project path;
- checks whether `openspec/` already exists to decide extend mode;
- detects/removes legacy artifacts;
- selects tools;
- creates directory structure;
- generates skills/commands;
- creates config when appropriate;
- prints a summary.

## AI tool integrations generated by init

OpenSpec init configures selected tools by generating skills and/or commands. It does not copy static files from a folder; it renders in-code templates.

Important mechanics:

- `src/core/init.ts:494-568` reads global profile/delivery settings, filters workflows, and writes selected skills/commands.
- `src/core/profiles.ts:8-22` defines core workflows (`propose`, `explore`, `apply`, `sync`, `archive`) and expanded workflows (`new`, `continue`, `ff`, `bulk-archive`, `verify`, `onboard`).

## Idempotency, refresh, and cleanup behavior

OpenSpec init is intentionally reusable:

- Existing `openspec/` means extend mode (`src/core/init.ts:139-151`).
- Directory creation re-ensures the same directories.
- Generated skill and command files are overwritten/refreshed for selected tools because `FileSystemUtils.writeFile()` creates parents and writes content unconditionally (`src/utils/file-system.ts:197-201`).
- Existing `openspec/config.yaml` / `.yml` is not overwritten (`src/core/init.ts:598-607`).
- `--tools none` can create only the OpenSpec structure/config without tool integrations (`test/core/init.test.ts:210-225`).
- Delivery changes can remove previously generated managed skills or command files (`src/core/init.ts:531-553`, `src/core/init.ts:746-783`).

Legacy cleanup is a major part of init:

- `src/core/legacy-cleanup.ts:14-66` detects legacy config and slash-command artifacts.
- `src/core/legacy-cleanup.ts:359-393` removes OpenSpec marker blocks and old command files.
- `src/core/legacy-cleanup.ts:396-421` deletes legacy `openspec/AGENTS.md`.
- `src/core/legacy-cleanup.ts:633-650` advises migrating `openspec/project.md` content into `openspec/config.yaml` `context:`.

## Schema-driven artifact initialization

OpenSpec does not hard-code proposal/spec/design/task content in the init command. Instead, built-in schemas and templates define what artifacts agents should create.

Default `spec-driven` schema:

- `schemas/spec-driven/schema.yaml:1-9` defines the default proposal artifact generating `proposal.md`.
- `schemas/spec-driven/schema.yaml:30-83` defines change-local delta specs generating `specs/**/*.md` and requiring proposal.
- `schemas/spec-driven/schema.yaml:85-111` defines `design.md`.
- `schemas/spec-driven/schema.yaml:113-146` defines `tasks.md` requiring specs and design.
- `schemas/spec-driven/schema.yaml:148-153` defines apply requirements over `tasks.md`.

Templates:

- `schemas/spec-driven/templates/proposal.md:1-23`
- `schemas/spec-driven/templates/spec.md:1-8`
- `schemas/spec-driven/templates/design.md:1-19`
- `schemas/spec-driven/templates/tasks.md:1-9`

The schema instructions are strict about spec format:

- change-local specs use `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements`, and `## RENAMED Requirements` (`schemas/spec-driven/schema.yaml:42-45`);
- requirements use `### Requirement: <name>` (`schemas/spec-driven/schema.yaml:48`);
- scenarios use exactly `#### Scenario: <name>` (`schemas/spec-driven/schema.yaml:50-51`);
- MODIFIED requirements must include the full updated requirement block copied from `openspec/specs/<capability>/spec.md` (`schemas/spec-driven/schema.yaml:54-61`).

## Durable spec initialization and archive/sync behavior

Durable specs live under `openspec/specs/<capability>/spec.md` and are the source of truth for current behavior.

Docs:

- `docs/getting-started.md:23-47` describes `openspec/specs/` as source of truth and `openspec/changes/` as proposed updates.
- `docs/concepts.md:28-50` explains specs vs changes.
- `docs/concepts.md:196-264` defines spec structure: `## Purpose`, `## Requirements`, `### Requirement:`, `#### Scenario:`.
- `docs/concepts.md:280-321` emphasizes specs are behavior contracts, not implementation plans.

Applying deltas:

- `src/core/specs-apply.ts:57-78` scans `changeDir/specs/<capability>/spec.md` and maps it to `mainSpecsDir/<capability>/spec.md`.
- `src/core/specs-apply.ts:102-225` parses delta specs, rejects duplicates/conflicts, and requires at least one delta.
- `src/core/specs-apply.ts:244-306` applies operations in the order `RENAMED → REMOVED → MODIFIED → ADDED`.
- `src/core/specs-apply.ts:353-368` writes updated durable spec files.
- `src/core/specs-apply.ts:374-377` creates a skeleton for a new durable spec:

```md
# <Capability> Specification

## Purpose
TBD - created by archiving change <change>. Update Purpose after archive.

## Requirements
```

Archive:

- `src/core/archive.ts:56-64` requires `openspec/changes`; if absent, it tells users to run `openspec init` first.
- `src/core/archive.ts:133-151` validates change delta specs and blocks archive on invalid deltas.
- `src/core/archive.ts:201-253` builds and writes spec updates unless `--skip-specs`.
- `src/core/archive.ts:267-285` moves the change into `openspec/changes/archive/<date>-<change>`.

Docs:

- `docs/getting-started.md:113-117` explains ADDED/MODIFIED/REMOVED archive effects.
- `docs/getting-started.md:201-228` shows archive merging specs into `openspec/specs/ui/spec.md` and moving the change to archive.
- `docs/workflows.md:279-305` says archive prompts if specs have not been synced.

## Validation behavior related to initialized specs

Validation discovers items from initialized directories:

- `src/utils/item-discovery.ts:4-20` active changes are directories in `openspec/changes/`, excluding `archive`, that contain `proposal.md`.
- `src/utils/item-discovery.ts:22-42` specs are `openspec/specs/<id>/spec.md`.
- `src/commands/validate.ts:105-145` dispatches validation for active changes and specs.
- `src/commands/validate.ts:184-212` performs bulk validation.
- `src/core/validation/validator.ts:92-279` validates delta specs.
- `src/core/validation/validator.ts:282-317` validates main specs.

Key detail: a newly initialized empty `openspec/specs/` directory is valid as a container, but there are no durable spec docs until a domain spec exists or a delta archive creates one.

## Important takeaways for Cartographer

1. OpenSpec init is broader than a single requirements doc initializer. It bootstraps a project home, durable/current specs directory, changes directory, archive directory, config, and AI tool integrations.
2. OpenSpec does not generate actual durable spec docs until domains/capabilities exist; it creates the container early and creates new spec files during sync/archive from deltas.
3. OpenSpec's durable spec skeleton is more behavior-contract-oriented than Cartographer's current one-line `docs/requirements.md` header.
4. OpenSpec separates init from change creation. `openspec init` creates the home; `openspec new change` creates a specific change directory with `.openspec.yaml` metadata.
5. OpenSpec's artifact instructions are schema-driven. Cartographer currently has workflow docs and graph validators, but not a schema/template instruction loader equivalent for requirements docs.
6. OpenSpec has strong idempotency semantics: refresh generated managed files, preserve config, and do not overwrite user spec content unless applying validated deltas.
